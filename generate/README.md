# SD-JWT Interop tool

This tool is used to verify interoperability between `sd-jwt-rust` and the `sd-jwt-python` and `sd-jwt-js`
implementations of the
[IETF SD-JWT specification](https://datatracker.ietf.org/doc/draft-ietf-oauth-selective-disclosure-jwt/).

## How does the Interop tool work?

The main idea is to generate data structures (SDJWT/presentation/verified claims) using both implementations and compare
them.

The reference implementation (`sd-jwt-python` or `sd-jwt-js`) is used to generate artifacts based on input data
(`specification.yml`) and store them as files. The interop tool (based on `sd-jwt-rust`) is used to generate
artifacts using the same specification file, load artifacts stored in files by the reference implementation and
compare them. The interop tool doesn't store any files on filesystem.

`sd-jwt-js` ships no such generator, unlike `sd-jwt-python`'s own `generate.py`, so `generate/js/generate.mjs` plays
that role here: it reads the same `specification.yml`/`settings.yml` fixtures (they're plain YAML, not
`sd-jwt-python` code) and writes the same artifact files, using `@sd-jwt/core` as the reference implementation.

There are some factors that make impossible to compare data due to non-equivalence data generated by different
implementations:

- Using random 'salt' in each run that make results different even though they are generated by the same implementation.
- Not equivalent json-serialized strings (different number of spaces) generated under the hood of the different
  implementations.
- Using 'decoy' digests in the SD-JWT payload.

In order to reach reproducibility and equivalence of the values generated by both implementations it is required to use
the same input data (issuer private key, user claims, etc.) and to get rid of some non-deterministic values during data
generating (values of 'salt', for example).

### Deterministic 'salt'

In order to make it possible to get reproducible result each run it's required to use deterministic values of 'salt'
used in internal algorithms. The `sd-jwt-python` project implements such behavior for test purposes.

In order to use the same set of 'salt' values by the `sd-jwt-rust` project Python-implementation stores values in the
`claims_vs_salts.json` file as artifact. The Interop tool loads values from the file and use it instead of random
generated values (see the `mock_salts` feature).

### Similar json serialization

In order to have the same json-strings used under the hood of the both implementations there is some code that gets rid
of different number of spaces:

```rust
value_str = value_str
  .replace(":[", ": [")
  .replace(',', ", ")
  .replace("\":", "\": ")
  .replace("\":  ", "\": ");
```

`sd-jwt-python`'s `json.dumps` puts a space after `:` and `,`; `sd-jwt-js`'s `JSON.stringify` doesn't. The `--reference`
flag (`python`, the default, or `js`) tells the interop tool which convention to match when it re-serializes a
disclosure's value under `mock_salts`, so the digest it computes lines up with the loaded reference's own digest (see
`MOCK_DISCLOSURE_PYTHON_SPACING` in `src/utils.rs`).

### 'Decoy' SD items

In order to make it possible to compare `SD-JWT` payloads that
contains [decoy](https://www.ietf.org/archive/id/draft-ietf-oauth-selective-disclosure-jwt-07.html#name-decoy-digests).
it was decided to detect and remove all `decoy` items from payloads and then compare them.

## How to use the interop tool?

1. Install the prerequisites.
2. Clone and build the `sd-jwt-rust` project.
3. Clone, build and generate artifacts with the `sd-jwt-python` project.
4. Generate artifacts with `sd-jwt-js` (reuses the fixtures from step 3).
5. Run the interop tool against each reference implementation.

### Install the prerequisites

In order to be able to build both implementations it is required to setup following tools:

- `Rust` & `cargo`;
- `poetry` (for `sd-jwt-python` reference impl);
- `Node.js` & `npm` (for `sd-jwt-js` reference impl).

### Clone and build `sd-jwt-rust` project

```shell
git clone git@github.com:openwallet-foundation-labs/sd-jwt-rust.git
cd sd-jwt-rust/generate
cargo build
```

### Clone, build and generate artifacts with `sd-jwt-python` project

`setup_sd_jwt_python.sh` clones `sd-jwt-python` at a pinned revision,
applies `sd_jwt_python.patch`, builds it, and generates the test
case/example artifacts that sd-jwt-rust is compared against.

It is safe to re-run `setup_sd_jwt_python.sh`.

```shell
./setup_sd_jwt_python.sh <target-dir>
```

This writes the resolved clone path to `.sd-jwt-py-path` (git-ignored), used below.

### Generate artifacts with `sd-jwt-js`

`setup_sd_jwt_js.sh` copies the `specification.yml`/`settings.yml` fixtures written by
`setup_sd_jwt_python.sh` (step above; they're plain YAML fixtures, not `sd-jwt-python` code, so they're reused rather
than duplicated) into `<target-dir>`, then runs `generate/js/generate.mjs` over them - `sd-jwt-js` has no test-vector
generator of its own to shell out to, so this script's `generate.mjs` plays that role using `@sd-jwt/core` directly.

It is safe to re-run `setup_sd_jwt_js.sh`.

```shell
./setup_sd_jwt_js.sh <target-dir>
```

This writes the resolved path to `.sd-jwt-js-path` (git-ignored), used below.

### Run the interop tool

```shell
cd sd-jwt-rust/generate
cargo build
./run_interop_py.sh      # against sd-jwt-python
./run_interop_js.sh      # against sd-jwt-js
```
